01Summary

Airflow's ObjectStoragePath lets you work with files in cloud storage the way you'd work with local paths. For Azure Data Lake Storage Gen2 there's a common way to connect: a service principal, with the storage account name in Host and the client ID in Login. The ADLS hook worked with that connection. ObjectStoragePath failed on it with a ValueError. It was reported in June 2024 as issue #40410.

I changed how the ADLS filesystem reads that connection, kept every other kind of connection on its old path, added tests and wrote a docs page for it. Four people reviewed or tested it over five months, and it was merged into main on Nov 20, 2026.

02The issue

Issue #40410 was opened on Jun 24, 2024. It put two connections side by side. A connection string in Extra worked for both the ADLS hook and ObjectStoragePath. A service principal didn't. The hook connected, and ObjectStoragePath raised an error from adlfs, the library Airflow uses for Azure storage.

The issue also pointed out there was no documentation for ObjectStoragePath on Azure at all. It was labelled a good first issue, and in 2025 another user wrote in the thread that they'd run into the same thing.

03Root cause

get_fs() turns an Airflow connection into an adlfs filesystem. It built an account URL with parse_blob_account_url(conn.host, conn.login) and passed it on as account_url.

Two things went wrong with a service principal. When Host is a bare account name like mystorageaccount, there's no dot in it, so the helper builds the URL from Login instead, and for a service principal Login is the client ID. On top of that, AzureBlobFileSystem doesn't take an account_url at all. adlfs dropped it and was left with no account name, which is the error in the issue.

The second part came out in review: Aaron Chen and Jarek Potiuk read the adlfs source and showed that account_url lands in **kwargs and is never used.

A passed account_url= lands in **kwargs and is dropped; adlfs then derives self.account_url itself from account_host or account_name, so with no account_name it builds https://None.blob.core.windows.net.

Jarek Potiuk (@potiuk) · Aug 29, 2026

04The fix

#68344, opened Jun 10, 2026. For an adls connection whose Host is a bare account name, get_fs() now passes account_name. A small helper, _bare_account_name_from_host, decides whether Host is a bare name: no dot, no scheme, no port and no path.

Everything else stays on the old account_url path: wasb connections, full URLs and custom endpoints. So nothing that worked before changes.

The PR also adds a docs page for ObjectStoragePath on ADLS, with its URL formats and the connection fields it reads, and fixes the Host description in the ADLS V2 connection docs.

05Backward compatibility

David Blain reviewed it two days after I opened it. My first version swapped account_url for account_name on every connection, and he asked what that meant for existing connections, custom endpoints in particular.

He had a point. Eight minutes later I pushed a change that kept account_url for wasb, full URL and custom endpoint connections, and limited the new behavior to the case from the issue: an adls connection with a bare account name in Host. I added a test for each of those four kinds of connection.

Provider connection changes should always remain backward compatible, and existing connections must not be impacted by an upgrade.

06Review

Jarek Potiuk reviewed it at the end of July. He agreed with the diagnosis and with scoping it to adls connections, and left three things inline: the bare-host check was case-sensitive in a surprising way, two helper functions had dead logic between them, and the newsfragment file had to go, because providers don't use them.

The next day Aaron Chen pointed out that AzureBlobFileSystem has no account_url parameter. On Aug 6 I collapsed the two helpers into one that compares against host.lower(), added a test for a mixed-case host like MyAccount, wrote a comment on the one case that sets no account at all, and removed the newsfragment.

Jarek's next review, on Aug 29, said that round was addressed. He flagged one test that still asserted the account_url key that adlfs ignores.

the diagnosis is right: for an adls Active Directory connection login is the AD client_id, so a bare host really does need to become account_name rather than being folded into an account URL.

Jarek Potiuk (@potiuk) · Jul 29, 2026

07Live check

Aaron asked to see the fix work against real Azure. Xiaolong Song, another contributor, ran it on Oct 11 against a real ADLS Gen2 account, with the same connection as the issue: the account name in Host and a service principal in Login, Password and tenant_id.

He ran it twice in the same image, once on main and once on main with this PR merged in. On main, get_fs() failed with the error from the issue. With the PR it listed the container, wrote a file, read it back and deleted it. Aaron approved the same day.

Output from Xiaolong's check on the PR, Oct 11, 2026 (the write result is shortened).

08Final round

On Oct 30 Xiaolong summed up what was left and offered to finish it in a follow-up PR if I was short on time. I picked it back up and pushed the changes on Nov 2.

The custom-domain test became an account_host case, which is a real adlfs parameter. The full-endpoint case became a direct test of the bare-host helper.

On Nov 17 David reviewed the whole thing again. He listed everything that was addressed and three open points, all in the docs and one code comment. I fixed all three that day, and he approved it on Nov 18.

The account_url path that stays for wasb connections and full-URL hosts was out of scope here. David opened #77371 to track it before he merged.

09Tests

test_get_fs covers an ADLS connection with a bare account name and a service principal, the same with an account key, a mixed-case host, a custom domain through account_host, the no-host case, and wasb connections that still get account_url.

A separate test checks the helper directly with a dotted host, a scheme, a port, a path, an empty string and None.
